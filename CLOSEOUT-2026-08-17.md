## T1.4 - fresh-VM verification, and where it stops

A clean VM in a different metro, with no collector state: **9.8 GB disk, no `/root/.config`, no
credentials of any kind.** From it:

- The committed manifest fetched unauthenticated: **HTTP 200**, totals matching.
- Three objects chosen at random from it (seed 1404): `KXNOBELPEACE`, `KXATPSETWINNER`, `KXBNB15M`.
- Unauthenticated R2 reads of all three: **HTTP 400**. So did the impossible control key. **An
  unauthenticated 400 is a statement about the request, not about the resource** - it carries no
  information about whether the object exists, which is the fourth-layer trap in a new costume.

**The authenticated half cannot run.** Not because of an error - because Gate 0 line 1 is NO ROUTE
by construction, and a fresh VM therefore has no way to obtain the keys. This is the durability
finding, stated plainly:

> The dataset survives the machine. The **ability to verify it** does not. R2 holds the objects
> independently of any VM - Gate 0 line 3 already proved that, reading data written by a destroyed
> VM back byte-identical from a fresh VM in another metro. But the credential that opens R2 lives
> only inside the VM it was pasted into, so the machine that writes the data is also the only
> machine that can confirm the data is fine. Destroying the collecting VM before writing the
> close-out would have destroyed the ability to commit the close-out.

That is why this document was committed **before** the collecting VM was destroyed, and it is a
deliberate, stated deviation from T1.4's ordering rather than a slip. The mitigation already
chosen - commit every artefact as it is produced - is what made the cost of it zero: every
artefact from this session was committed within seconds of existing.

**Outstanding, needs one paste:** R2 credentials into a fresh session, after which the
re-download-and-hash of the three named objects takes under a minute.
